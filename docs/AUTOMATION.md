# Automation — nothing to do by hand after the first push

Every store generated by `npm run new-client` ships three GitHub Actions workflows that need **no secrets**
(they read the public Supabase URL / publishable key from `assets/js/config.js`, which every visitor receives anyway):

| Workflow | When | What |
|---|---|---|
| `keepalive.yml` | every 3 days | one anon read → the free Supabase project never pauses |
| `content-backup.yml` | Mondays | `scripts/content-backup.mjs` → `backups/content-YYYY-MM-DD.json` committed (published state, catalog, pages, approved reviews; keeps 12). Orders/customers are not anon-readable by design → `docs/BACKUP.md` or the dashboard JSON backup |
| `template-update.yml` | daily | **pull mode**: checks the template's latest GitHub release; if newer, runs `scripts/update-from-template.mjs`, and pushes only if `npm run check` passes → Cloudflare Pages / Vercel redeploys. Private template repo → secret `TEMPLATE_TOKEN` (fine-grained PAT, Contents: read) per client **or** at organisation level once |

And the template itself has `release.yml` — **push mode**, zero per-client setup:

```
npm run release -- 1.8.0      # bumps version, runs check:full, commits, tags v1.8.0
git push && git push --tags   # → GitHub release → every repo in clients.json is cloned, updated, checked, pushed
```
One secret, once, in the template repo: `CLIENTS_TOKEN` (fine-grained PAT, Contents: read/write + Issues: write on the
client repos). `new-client --repo owner/name` registers the store in `clients.json` automatically.

## What an update touches — and what it never touches
`scripts/lib/client-sync.mjs` is the single definition. Never overwritten or deleted:
`assets/js/config.js`, `assets/js/brand.config.js`, `CLIENT.md`, `LICENSE-CLIENT.txt`, `supabase/ALL_IN_ONE.sql`,
`.env*`, `backups/`. Everything else is template-owned: it is replaced, and files the previous template version owned
(`template-manifest.json`) but the new one dropped are deleted. Then: `package.json` re-derived, `apply-brand`
(titles, logos, `_headers`, sitemap from the merchant's `brand.config.js`), Prettier, `npm run check`.

## The one thing a robot cannot do
New SQL migrations need the database password. The update still ships the code; the workflow opens a GitHub issue
listing the files to paste into Supabase → SQL Editor (idempotent, in order). `npm run update:check` (dry-run) shows
the plan for the next release at any time.

## First-time for an existing store (e.g. demo1 on 1.5.3)
The workflows live in the repo, so the first 1.7.0 patch must be pushed once by a human (`apply-patch.cmd` in the patch
does it in one double-click). From then on everything above is automatic.
